# Stack & Folder Structure — varels_cms

> This file is the authoritative stack + folder-structure spec. There is no
> separate `tech-stack.md` or `folder-structure.md`; the tree below reflects the
> actual repository layout.

---

## 1. Why not DDD / Clean Architecture

For this stack (Go, HTMX, Templ, sqlc, SQLite) and an AI-driven workflow, a
textbook Domain-Driven Design (DDD) / Clean Architecture layout
(`domain`, `application`, `infrastructure`, `interfaces`) makes life harder, not
easier.

While DDD is great for massive enterprise apps, it is an anti-pattern for
HTMX + sqlc + AI:

- **The sqlc mapping nightmare.** sqlc automatically generates perfect Go structs
  from the database. In DDD you are not supposed to leak database structs into the
  application layer, so you force the AI to write boilerplate mapping
  `infrastructure/persistence.User` → `domain/entity.User` →
  `application/dto.User`. You lose all the speed of sqlc.
- **HTMX loves locality of behavior.** HTMX apps are essentially
  server-side-rendered. You want your route, database call, and HTML template
  (`.templ`) as close together as possible. Spreading them across
  `infrastructure`, `application`, and `interfaces` means jumping between five
  files just to add a single button.
- **AI context limits.** With Spec-Driven Development, asking the AI to "add a
  feature" makes it generate code for six different nested folders. It will
  hallucinate, forget interfaces, and get confused.

For Go, chi, templ, HTMX, and sqlc, you want a structure that is **flat,
pragmatic, and highly cohesive**.

> **Updated.** The codebase later adopted a lighter version of this idea: HTTP
> concerns are grouped under `internal/handlers` by category, and two *thin*
> shared layers were added (`internal/service` for cross-package business logic,
> `internal/repository` for shared reads over sqlc). sqlc is still the database
> layer and feature handlers still call it directly; the new layers exist only
> for logic reused by more than one handler package, not as a full DDD stack.

### What changed from the original structure

- **DELETED `internal/models/`** — sqlc auto-generates structs directly from the
  database schema; you no longer write these manually.
- **`internal/repository/` returns as a thin shared data-access layer** — sqlc
  auto-generates the database methods (e.g. `Queries.CreateProduct`) and handlers
  call those directly for feature queries. Only helpers reused by more than one
  handler package live here: shared reads (`LocationNames`, aggregate
  normalisation) and the `WithTx` transaction primitive. It is not a second ORM.
- **`internal/service/` returns for shared business logic** — FIFO costing,
  order numbering, IVA derivation and the clock. Logic used by a single handler
  package stays in that package; only cross-package business rules live here.
- **MOVED `internal/validation/`** — validators are now helper functions inside
  `handlers/`, right next to the HTTP logic that uses them.
- **RENAMED `static/` → `assets/`** — to match the recommended standard (keep
  `static/` if you prefer).
- **MOVED `views/` into `internal/`** — keeps the public root clean and treats UI
  components as internal application code.
- **SPLIT `internal/handlers/` by category** — shared HTTP concerns live in
  `handlers/common` (the `Server`, rendering, form parsing, audit, transactions),
  middleware in `handlers/middleware`, and HTTP handlers are grouped by category
  (`catalog`, `sales`, `inventory`, `finance`, `analytics`, `admin`, `authweb`).
  Each category package defines its own `Server` that embeds `*common.Server`;
  category packages do not import each other, and the shared layers never import
  a handler package, so the dependency graph stays acyclic.

### Layer boundaries

| Concern | Package |
| --- | --- |
| Shared HTTP kernel (Server, render, forms, audit, tx) | `internal/handlers/common` |
| HTTP middleware (Logger, Recover, RequestID, CSRF) | `internal/handlers/middleware` |
| Business logic (FIFO costing, order numbers, IVA) | `internal/service` |
| Shared DB reads + transactions over sqlc | `internal/repository` |
| Reporting time ranges | `internal/reporting` |
| Category HTTP handlers | `internal/handlers/<category>` |
| Cross-package tests | `internal/handlers/tests` |

Random one-off utilities should not accumulate in `common`; give them a specific
home or keep them next to their only caller.

## 3. Why this is a massive upgrade

- **The "golden triangle".** To add a product feature you touch only three places:
  1. `internal/db/queries/products.sql` — write the SQL
  2. `internal/handlers/catalog/product_handler.go` — write the Go logic
  3. `internal/views/pages/product_detail.templ` — write the UI
- **Zero boilerplate.** With `models/` and `repository/` gone, you no longer map
  `sqlc.Product` to `models.Product`. A handler calls
  `db.GetProduct(ctx, id)` and passes the result straight to
  `views.ProductDetail(product)`.
- **AI-friendly.** Paste `products.sql`, `product_handler.go`, and
  `product_detail.templ` into one prompt; the AI sees your schema, logic, and UI
  at once without running out of context or hallucinating missing interfaces.

### Why this structure is 10x better for your AI

- **One-stop DB layer.** Tell the AI "I need a new feature," paste
  `internal/db/schema.sql`, and say "write the query in `query.sql`." It knows
  exactly where it goes.
- **No DTOs.** Chi handlers (`internal/handlers/catalog/product_handler.go`) call
  `db.GetProduct()`
  and pass the raw `db.Task` struct straight into `views.Dashboard(tasks)`. Zero
  mapping, insanely fast to write and generate.
- **Perfect context windows.** When a feature breaks, look at three files: the DB
  query (`query.sql`), the handler (`tasks.go`), and the view (`dashboard.templ`).
  Paste all three into the prompt to fix bugs.

## 4. The stack, component by component

### 4.1 Styling — Tailwind CSS (standalone CLI)

You need a way to make the CMS look like a clean, modern SaaS app without writing
thousands of lines of custom CSS.

- **Why it fits:** Tailwind pairs naturally with templ. You write standard utility
  classes directly inside your `.templ` components.
- **Pro-tip for Go:** Don't install Node.js just for CSS. Download the official
  Tailwind Standalone CLI binary and your project stays 100% free of npm and
  `node_modules`.

### 4.2 Database layer — sqlc (type-safe SQL compiler)

Raw SQL in Go leads to typos; heavy ORMs (like GORM) can be slow and hide what's
happening.

- **Why you need it:** You write pure, standard SQLite queries in a `.sql` file
  and sqlc generates 100% type-safe Go code for you.
- **Why it's perfect for AI:** AI writes fantastic raw SQL. Tell it "write the SQL
  to get the best-selling hoodies by month" and sqlc turns it into exact Go
  methods for your database.

### 4.3 Migrations — golang-migrate or goose

The app tracks real physical inventory and financial records, so you can't just
delete the SQLite database to add a column (e.g. a barcode) next month.

- **Why you need it:** A migration tool applies incremental schema changes safely,
  without wiping stock counts or sales history. **goose** is currently the
  community favorite in the Go ecosystem.

### 4.4 Dev tooling — Air (live-reloading)

In standard Go, every template or Go-file change forces a stop, recompile, and
restart.

- **Why you need it:** Air watches your `.go` and `.templ` files. The second you
  save, it re-compiles templ, builds the binary, and refreshes the server in
  milliseconds — the instant feedback loop of modern web development.

### 4.5 Charts — ApexCharts or Chart.js (CDN link)

The CMS must show sales per year, per month, and profit margins; a raw table of
numbers is hard to digest.

- **Why you need it:** Add a single `<script>` tag in `layouts/base.templ`. When
  HTMX pulls sales data from SQLite, render smooth line graphs (revenue over time)
  and bar charts (top-selling shirts vs. pants) with almost zero JavaScript.

### 4.6 Frontend dynamics — HTMX + Alpine.js

HTMX handles server-driven partial updates (search, filters, table rows, flash),
while Alpine.js 3.x handles small local UI state (dropdowns, the multi-line POS
editor, toggles) without a SPA framework.

- **Where they live:** both are browser assets, so they are **not** in `go.mod`.
  They are vendored into `assets/js/` (`htmx.min.js`, `alpine.min.js`) and loaded
  from `layouts/base.templ` — same zero-npm, self-hosted approach as the rest of
  the stack (ADR-0022).
- **Glue — `assets/js/app.js`:** listens for `htmx:afterSwap` to re-initialise
  Alpine on swapped fragments, and turns HTMX request failures into toasts in the
  `#flash` region. Alpine components can call `$store.app.flash(msg)`.
- **Flash messages:** session-backed and rendered once by the layout into
  `#flash`; HTMX mutation responses swap it out-of-band (`partials.FlashOOB`).
- **Alpine components:** the POS line editor (`pos()` in `app.js`, used by
  `pages/sale_form.templ`) is the reference example — reactive line items and a
  running total with no build step.

## 5. Summary

| Layer             | Tool                         | Purpose                                                 |
| ----------------- | ---------------------------- | ------------------------------------------------------- |
| Language & Router | Go + go-chi                  | High-performance backend & routing                      |
| Templating        | templ                        | Type-safe, compiled HTML components                     |
| Frontend Dynamics | HTMX (2.x) + Alpine.js (3.x) | Partial-page updates + local component state (vendored) |
| Styling           | Tailwind CSS (Standalone)    | Modern dashboard UI (zero npm)                          |
| Database          | SQLite + sqlc                | Zero-config database with type-safe Go queries          |
| Schema Changes    | goose                        | Safe database migrations                                |
| Auth              | Goth + SCS                   | Free Google OAuth & secure sessions                     |
| Dev Tooling       | Air                          | Instant hot-reloading on save                           |

This entire stack compiles into a single self-contained binary plus a single
SQLite file. It can be deployed to a $4/month server (Hetzner, Fly.io) and run
blazingly fast.
